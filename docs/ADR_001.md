# ADR 001 : architecture cible du projet AlzheimerDataHub

- **Statut :** accepté
- **Date :** 06/11/2026 (mis à jour le 07/11/2026)
- **Auteure :** Wiem Ben M'sahel

## Contexte

Un chercheur ou data analyst en santé veut savoir quels indicateurs cliniques (MMSE, tension,
cholestérol, âge) distinguent les patients diagnostiqués Alzheimer. Deux sources de nature
différente sont disponibles :

- **Patients** : un CSV tabulaire de 2149 lignes (Kaggle, jeu synthétique, CC BY 4.0), schéma fixe.
- **Littérature** : des articles PubMed (API NCBI, XML), semi-structurés (nombre variable de termes
  MeSH, champs parfois absents), 195 articles distincts.

Il n'existe aucune clé commune entre les deux sources.

## Exigences

| Id | Exigence | Mesure |
|---|---|---|
| E1 | Données brutes conservées et rejouables | copie horodatée dans `data/raw/` |
| E2 | Qualité contrôlée, rejets conservés | au moins 5 règles automatisées, fichiers `rejected` |
| E3 | Relance sans doublon | clé métier + UPSERT, 1963 patients et 195 articles après N exécutions |
| E4 | Indicateurs interrogeables par un utilisateur non développeur | vues SQL + tableaux de bord |
| E5 | Reproductible par un tiers | README, installation en quelques commandes, pas de secret |
| E6 | Panne détectée, preuves conservées, reprise possible | statut FAIL, `runs`, logs, reprise depuis le raw ou `--resume` |
| E7 | Proportionné au besoin | petits volumes (quelques milliers de lignes), traitement à la demande |

## Options comparées

### Stockage

| Option | Description | Points forts | Points faibles |
|---|---|---|---|
| A. Fichiers seuls | CSV et JSONL dans `data/`, analyse en pandas | Très simple, zéro dépendance | Pas de contrainte de clé, pas de requêtes KPI partagées, pas de droits, idempotence à coder à la main |
| B. PostgreSQL seul | Patients en tables, articles dans une colonne JSONB | Un seul système, un seul modèle de droits, jointures SQL possibles | JSONB moins naturel pour des documents à structure variable ; ne montre pas deux modèles de données |
| C. PostgreSQL + MongoDB Atlas | Patients en relationnel, articles en documents | Chaque modèle sert la forme de sa donnée, UPSERT sur `pmid`, offre gratuite | Deux systèmes à opérer, dépendance à un service externe |
| D. MongoDB seul | Tout en documents | Un seul système | Perd les contraintes relationnelles, la clé primaire et les vues SQL pour des données qui sont tabulaires |

Une option « entrepôt de données complet ou Data Lake distribué » a été écartée sans comparaison
détaillée : le volume (quelques milliers de lignes) ne le justifie pas (E7).

### Orchestration

| Option | Description | Points forts | Points faibles |
|---|---|---|---|
| 1. Lancement manuel | Chaque script lancé à la main | Aucun code en plus | Ordre et dépendances à retenir, pas de reprise ciblée, erreurs humaines |
| 2. DAG minimal en Python | `src/run_all.py`, bibliothèque standard (`graphlib`) | Dépendances explicites, propagation des échecs, reprise `--resume`, aucun service à installer | Pas d'interface graphique, pas de planification |
| 3. Airflow ou Prefect | Orchestrateur dédié | Planification, interface, relances automatiques | Serveur et base de métadonnées à opérer, disproportionné pour 5 tâches sur une machine |

### Mode de traitement : batch, streaming ou hybride

| Option | Description | Points forts | Points faibles |
|---|---|---|---|
| a. Batch | Traitement à la demande d'un fichier complet | Simple, rejouable, adapté à des sources figées | Une panne n'est détectée qu'à la fin du fichier |
| b. Streaming | Traitement événement par événement, en continu | Détection précoce d'une dérive, faible latence | Infrastructure (file de messages, supervision) sans source qui émet en continu |
| c. Batch + simulation de flux | Batch pour la chaîne principale, flux simulé à partir du fichier figé | Montre l'apport du continu sans l'imposer, vérifiable contre le batch | Preuve de concept seulement, aucune source réelle en continu |

### Restitution

| Option | Description | Points forts | Points faibles |
|---|---|---|---|
| i. Vues SQL et Metabase seuls | BI directe sur la base | Aucun code à maintenir | Qualité, littérature et pipeline peu visibles |
| ii. Metabase + tableau de bord Streamlit | Interface Python complète (5 onglets) | Réunit indicateurs, qualité, littérature, modèle et DAG | Un composant de plus, lecture mise en cache 60 secondes |
| iii. ii + API REST en lecture seule | Accès programmatique (scripts, notebooks) | Réutilisation des données fiabilisées, testée | Aucun consommateur réel, pas d'authentification |

## Décision

**Option C** pour le stockage, **option 2** pour l'orchestration, **option c** pour le mode de traitement et **option iii** pour la restitution, avec une chaîne principale **batch** à la demande :

- **PostgreSQL** (SQLite en secours) pour les patients, avec vues SQL (couche gold) lues par Metabase.
- **MongoDB Atlas** pour les articles PubMed, clé `_id = pmid`.
- **Raw** en fichiers horodatés (rôle de lac de données léger), curated en CSV, table et JSONL.
- **Pipelines Python** distincts (`pipeline.py`, `pubmed.py`) pilotés par des contrats YAML (`data_contract.yaml`, `pubmed_contract.yaml`), avec rapports par run et logs.
- **DAG minimal** (`run_all.py`) de 5 tâches : `patients`, `pubmed`, `export_parquet`, `model`, `purge_dry_run`.
- **Export Parquet** et **modèle de classification** lisant la couche silver.
- **Docker Compose** pour PostgreSQL et Metabase.
- **Extensions de démonstration, hors chaîne principale et en lecture seule** : tableau de bord Streamlit (`app2.py`), API REST FastAPI (`api.py`) et simulation de flux (`stream_demo.py`).

## Arguments

| Composant | Exigence | Justification |
|---|---|---|
| PostgreSQL pour les patients | E3, E4 | Schéma fixe, clé primaire, `ON CONFLICT` pour l'idempotence, vues KPI, rôle lecture seule pour Metabase |
| MongoDB pour les articles | E3 | Documents à structure variable ; l'UPSERT sur `pmid` évite les doublons (195 documents après plusieurs exécutions) |
| Raw fichier horodaté + hash | E1, E6 | Rejouer sans retélécharger, preuve de ce qui a été reçu |
| Contrats YAML | E2, E5 | Règles, seuils et fraîcheur définis une fois, le code les lit (tests dédiés) |
| Table `runs` + rapports JSON | E6 | Historique des exécutions et des échecs |
| DAG minimal | E6, E7 | Ordre des dépendances, `UPSTREAM_FAILED`, reprise ciblée, sans service supplémentaire |
| Export Parquet | E4 | Format d'échange colonne pour d'autres outils d'analyse, produit depuis la couche silver |
| Modèle de classification | E4 | Montre quels indicateurs portent un signal ; lit uniquement le curated validé, graine fixée, rapport tracé par hash |
| Tableau de bord Streamlit | E4 | Rend visibles la qualité, les incidents, la littérature et le pipeline, en plus des KPI |
| API REST et simulation de flux | E6 (démonstration) | Extensions isolées : un échec de l'API ou du flux n'affecte pas le pipeline principal |
| Docker Compose | E5 | Trois commandes pour recréer l'environnement |
| Batch (chaîne principale) | E7 | Sources figées ou peu volatiles, aucun besoin de latence |

## API REST (extension)

L'API (FastAPI) offre un accès programmatique en lecture seule aux patients, aux KPI, à la qualité des exécutions
et au résumé de la littérature. Elle n'est pas nécessaire au projet : Metabase et les vues SQL servent déjà d'interface.
Elle est retenue comme démonstration d'un second mode de restitution et pour illustrer la sécurité d'une API de données
(aucune route d'écriture, validation des paramètres, requêtes paramétrées, réponse 503 si la base est indisponible,
tentative d'injection SQL testée).

- **Conséquence négative :** un composant de plus à maintenir ; aucune authentification ni limitation de débit,
  donc usage local uniquement.
- **Condition de réexamen :** ajouter une authentification et une limitation de débit avant toute exposition hors
  de la machine locale, ou supprimer l'API si aucun consommateur n'apparaît.

## Batch, streaming ou hybride

**Décision : batch** pour la chaîne principale. Les deux sources sont figées (jeu Kaggle, mise à jour « Never ») ou peu
volatiles (littérature), et traitées à la demande ; aucune ne produit de flux continu.

Une simulation de flux (`src/stream_demo.py`) rejoue la source ligne par ligne (un producteur dans un fil séparé, une file
d'attente) et applique à chaque événement les règles du contrat patients. Une alerte part si le taux de rejet d'une fenêtre
glissante de 100 événements dépasse 20 %. Elle montre ce qu'un traitement en continu apporterait (détection précoce d'une
dérive : alerte peu après l'événement 600 quand 200 événements sont corrompus) et vérifie la cohérence avec le batch :
sans dérive, mêmes volumes (2149 événements, 1963 acceptés, 186 rejetés). C'est une preuve de concept, hors de la chaîne
principale, qui n'écrit pas dans la base.

- **Conséquence négative :** le flux est simulé ; l'assumer clairement évite de présenter une technologie sans besoin réel.
- **Condition de réexamen :** une source qui émet réellement en continu (capteurs, API d'événements) et pour laquelle le
  délai de détection d'un incident compte.

## Réponses aux questions du guide

| Question | Réponse |
|---|---|
| Pourquoi cette source ? | Accessible légalement, licence claire (CC BY 4.0), schéma documenté, volume adapté ; PubMed pour situer les indicateurs dans la littérature |
| Pourquoi cette fréquence ? | Ponctuelle : le jeu Kaggle est figé (mise à jour « Never ») ; PubMed pourrait être relancé périodiquement |
| Quelles données restent brutes ? | Le CSV reçu et le XML PubMed, jamais modifiés |
| Clé métier ? | `patient_id` ; `pmid` pour les articles |
| Pourquoi SQL, NoSQL, fichiers ? | SQL pour le tabulaire, document pour la littérature, fichiers pour le raw (voir options) |
| Data Lake, Warehouse, Mart ? | Lac léger (raw) et mart (vues KPI) oui ; entrepôt historisé non : une seule source tabulaire figée, pas d'historisation à faire |
| Batch ou streaming ? | Batch pour la chaîne principale ; simulation de flux en démonstration (voir section dédiée) |
| Reprise après panne ? | Relance du pipeline, idempotent, depuis le raw conservé ; le curated n'est pas modifié en cas d'échec ; le DAG rejoue seulement les tâches non réussies (`--resume`) |
| Détecter donnée absente, invalide ou en retard ? | Contrôle de schéma, règles de qualité, seuil de rejet, âge du fichier source (patients) et de l'article le plus récent (PubMed) ; alerte en fenêtre glissante dans la simulation de flux |
| Responsable et durée de conservation ? | Wiem Ben M'sahel ; raw et rapports 90 jours (contrat `retention`) |

## Conséquences positives

- Chaîne complète et rejouable, prouvée par 41 tests (incidents, idempotence, DAG, PubMed, modèle, Parquet, API, flux) et par un rejeu sur un clone propre du dépôt.
- Chaque base correspond à la forme de sa donnée.
- Le pipeline principal ne dépend pas de MongoDB : un échec Atlas n'affecte pas les patients.
- La panne d'une tâche est isolée : les tâches indépendantes continuent, la reprise est ciblée (`reports/dag_demo_failure.json`).
- Les extensions (Streamlit, API, flux) sont en lecture seule et isolées : elles ne peuvent pas corrompre les données.

## Conséquences négatives

- Deux systèmes de stockage à documenter et à maintenir, pour un petit volume.
- MongoDB Atlas est un service externe : le correcteur doit créer son propre cluster ou utiliser le JSONL local.
- L'option B (PostgreSQL avec JSONB) aurait suffi techniquement pour 195 articles ; le choix de MongoDB
  suit la recommandation de l'enseignant et illustre l'hétérogénéité des modèles. Il n'est pas imposé par le volume.
- Pas de jointure entre patients et articles : le recoupement se fait par indicateur, à la main.
- Le DAG n'a ni interface graphique, ni planification, ni relance automatique.
- L'incident MongoDB (publication impossible) n'est pas couvert par un test automatisé.
- L'API et la simulation de flux ajoutent du code et des tests à maintenir sans répondre à un besoin réel du projet.

## Condition de réexamen

- Revenir à l'option B (un seul système PostgreSQL) si la littérature reste un volume de quelques centaines d'articles
  sans besoin de recherche textuelle.
- Passer du DAG minimal à Airflow ou Prefect si les sources deviennent collectées périodiquement ou si le nombre de tâches
  et de sources augmente nettement.
- Introduire un entrepôt historisé si une source évolue dans le temps.
- Passer au streaming pour la chaîne principale seulement si une source impose une latence mesurable.
- Ajouter authentification et limitation de débit à l'API avant toute exposition hors de la machine locale, ou la supprimer
  si aucun consommateur n'apparaît.
